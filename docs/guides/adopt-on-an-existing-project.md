# Adopt heraut on an existing project

Your project already has release tags, maybe a `CHANGELOG.md`, maybe another release tool. This guide
gets heraut to continue from where you are: the next version follows your last tag, and the changelog
keeps your history.

## 1. Match your tags

heraut finds the last release among the tags that carry its prefix: `v` for SemVer (`v1.2.0`), none
for CalVer (`2026.11.0`). If your tags look different, the first run says so:

```console
$ heraut version next
! no tag matches versioning.tag_prefix "v", but 2 tags look like versions with the prefix "" (e.g. 1.0.0): set versioning.tag_prefix: "" to continue from them
v0.1.0
```

`v0.1.0` would restart your history. Set the prefix the warning names:

```yaml
versioning:
  strategy: semver
  tag_prefix: ""           # your tags are 1.0.0, 1.1.0, …
```

```console
$ heraut version next
1.2.0
```

The next version now follows `1.1.0`. Check it before your first release: `heraut version next` changes
nothing. If your tags have another shape, such as `release-1.0.0`, set that prefix
(`tag_prefix: "release-"`).

## 2. Your existing changelog

heraut updates `CHANGELOG.md` section by section, using markers it writes itself
(`<!-- heraut-release: 1.2.0 -->`). A file written by another tool or by hand has none, so the first
`heraut changelog` stops instead of guessing:

```text
✗ [2/2] Generate changelog — generating changelog: changelog "CHANGELOG.md" has no heraut-release anchors (generated by another tool?); rebuild it with anchors and full PR attribution by running `heraut changelog --regenerate` (or `heraut release --regenerate-changelog`), after which incremental updates apply: no heraut-release anchors
```

Choose one of two ways:

- **Rebuild it from your tags:** `heraut changelog --regenerate` writes one section per existing release,
  from the commits between tags. The file is **replaced**: hand-written text, such as an intro paragraph
  or notes you added to a release, is not kept. Commit the old file first if you want to compare.
- **Keep the old file as it is:** rename it (for example to `CHANGELOG-before-heraut.md`) and link it
  from the new one. With no `CHANGELOG.md`, heraut writes a new one at your next release, with the
  earlier releases rebuilt from the tags.

Either way, run it before your first `heraut release`, look at the result, and commit it.

## 3. Coming from another release tool

heraut replaces the tool's whole release step: version, changelog, tag and forge release. Remove the
tool's configuration and CI job once heraut's first release has worked.

| You used | What carries over | What to check |
|---|---|---|
| semantic-release | Its default tags (`v1.2.0`) and conventional commits work as they are. | Its `CHANGELOG.md` has no heraut markers: see step 2. Plugins (npm publish, Slack…) become [hooks](release-pipeline-and-hooks.md). |
| release-please | Tags (`v1.2.0`) and conventional commits work as they are. | heraut releases from the branch you run it on: no release pull request. Its `CHANGELOG.md`: see step 2. |
| git-cliff | Your tags, whatever their shape: set `tag_prefix` (step 1). | heraut writes the changelog itself; its sections are set by `commits.types` and templates ([Customize the changelog](template-customization.md)). |
| Hand-made tags | Any `prefix + version` shape. | The commit messages: heraut computes the next version from [conventional commits](commit-conventions.md). |

## 4. The first release

```bash
heraut check                    # the config and your machine
heraut release --dry-run        # what the release would do, nothing written
heraut release
```

From then on every release continues the same history. [Getting started](../getting-started.md) covers
the rest of the setup; [Release from GitHub Actions](github-actions.md) and
[Release from GitLab CI/CD](gitlab-ci.md) move it to CI.

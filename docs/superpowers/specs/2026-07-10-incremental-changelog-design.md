# Incremental Changelog Generation (native) — Design

- **Date**: 2026-07-10
- **Status**: Approved (brainstorm) — pending implementation plan
- **Scope**: the `native` generator's changelog mode — make regeneration **incremental** (prepend
  only the new release's section) by default, with a `--regenerate` escape hatch that rebuilds and
  re-enriches the whole file. Builds on [ADR-0034](../../adr/0034-native-remote-enrichment.md) §5
  (O(1) enrichment) and [ADR-0037](../../adr/0037-native-template-api.md) (customizable header).

---

## Problem

`native.generateChangelog` **rewrites the entire `CHANGELOG.md`** on every run and enriches only
the newest (unreleased) section — historical sections render from git alone (ADR-0034 §5, keeping
API calls O(1)). git-cliff, by contrast, also full-regenerates but enriches *every* section it
renders, so its committed changelog carries `by @user` attribution throughout.

Consequence: switching a project (e.g. heraut itself) from git-cliff to native means the next
release rewrites `CHANGELOG.md` and **strips historical PR-author attribution** from all past
sections. That is a visible, one-time regression in the committed history.

There is also no `docs/specs/` document defining the changelog file structure; the format is
implicit in the generators.

## Decision

Give `native`'s changelog **two modes**, and formally define the changelog file structure.

1. **Incremental (default).** Render only the unreleased section (commits `latest_tag..HEAD` →
   the version being released), enrich just that section (O(1) API), and **splice** it into the
   existing file, leaving every other section verbatim. Historical attribution is preserved
   because past sections are never rewritten.
2. **Full regeneration (`--regenerate`).** Rebuild every section from all tags **and enrich every
   section** (batched per platform), then overwrite the file. This restores/refreshes full
   historical attribution and repairs any structural drift, at the cost of more API calls.

This is **native-only**. git-cliff is unchanged (it already full-regenerates with enrichment).

---

## Changelog file structure (formalized)

A native-managed `CHANGELOG.md` is:

```
<preamble>            # everything before the first section anchor — e.g. "# Changelog\n\n"
<anchor> <section>    # newest release
<anchor> <section>    # …older releases, newest-first
```

- **Preamble** — free-form content before the first anchor (the `# Changelog` title and any
  hand-written intro). Incremental mode preserves it verbatim.
- **Anchor** — a stable HTML comment on its own line immediately before each section:
  ```
  <!-- heraut-release: v0.49.0 -->
  ```
  It carries the release **tag** (not the display version). It is invisible in every Markdown
  renderer (GitHub included), mirroring git-cliff's own use of HTML comments (`<!-- 0 -->` for
  group ordering). It is emitted by the **assembly layer**, not by any template block, so it is
  structural and non-overridable — customizing the `header` block (ADR-0037) can neither remove it
  nor change its shape, which is what lets the splice parser stay independent of the visible header.
- **Section** — the rendered release: the `header` block (`## [version]…`) + groups + commits, as
  produced by `renderChangelogSection`. Per-section render output is **unchanged** by this feature
  (the anchor is added around it, not inside it).

## Incremental algorithm (default mode)

Given the target `version`/`tag` and the effective `Output` path:

1. Render the new section for `tag` (commits `latest_tag..HEAD`), enriched, and prefix it with its
   anchor `<!-- heraut-release: <tag> -->`.
2. Read the existing `Output` file and branch on its state:
   - **Missing or empty** → **bootstrap**: build all sections from all tags (anchored), enrich the
     newest only (today's default enrichment). Write. No warning — there is nothing to preserve.
   - **Contains ≥1 anchor** → **splice**:
     - Locate the first anchor. Everything before it is the preamble (kept).
     - If the first anchor's tag **equals** `tag` → **replace** that section (from its anchor up to
       the next anchor, or EOF) with the freshly rendered one — idempotent re-runs.
     - Otherwise → **insert** the new anchored section between the preamble and the first anchor.
     - Write; all other sections are untouched.
   - **Non-empty but has no anchor** (foreign / legacy file, e.g. a git-cliff-generated changelog)
     → **stop with an error**, do not modify the file:
     > `changelog <file> has no heraut-release anchors (generated by another tool?); run with
     > --regenerate to rebuild it with anchors and full PR attribution, after which incremental
     > updates apply.`
     During `heraut release` this aborts the run (the operator must consciously `--regenerate`
     once before switching to incremental).

Only the new section's commits are enriched → **O(1) API calls**, regardless of history length.

## Full regeneration (`--regenerate`)

Ignore the existing file's contents. Build every section from all tags (each anchored), enrich
**all** sections, and overwrite `Output`. Enrichment is batched per the existing drivers:

| Platform | Batch primitive | Cost for full history |
|----------|-----------------|-----------------------|
| GitHub   | GraphQL, 50 SHAs/query | O(commits / 50) |
| Azure    | one `pullrequestquery` POST | ~O(1) |
| GitLab   | per-commit `glab api` | **O(commits)** |

When full regeneration runs against a **GitLab** remote, the changelog pipeline step emits a
warning that enrichment is one API call per commit and may be slow / rate-limited. (The warning is
produced at the pipeline layer, which knows both the `--regenerate` flag and the remote platform,
keeping the generator a pure string producer.)

## Config surface

- CLI flags only (no `.heraut.yml` knob — YAGNI; incremental is always the default):
  - `heraut changelog --regenerate`
  - `heraut release --regenerate-changelog`
- The flag is plumbed to the native generator the same way the running version is: a `yaml:"-"`
  field on `config.ContentDriver` (e.g. `RegenerateChangelog bool`), set from `PipelineOpts` in the
  app layer. Non-native generators ignore it.

## Error handling

- **Foreign anchorless file in incremental mode** → error naming `--regenerate` (above); file
  untouched; aborts a release.
- **Malformed anchor** (e.g. a `<!-- heraut-release: -->` with no tag) is treated as *no usable
  anchor at that position*; if no usable anchor exists the file is treated as anchorless (→ the
  foreign-file error), never silently spliced into the wrong place.
- **Write failure** wraps the OS error (`writing changelog %q: %w`), as today.

## Determinism & testing

Anchors are tag-derived (no clock), so output stays deterministic. Tests:

- **Anchor emission** — every section is preceded by its `<!-- heraut-release: <tag> -->` line;
  the per-section render goldens are unchanged.
- **Incremental splice** — bootstrap (empty → full build), anchored-insert (new tag above top),
  anchored-replace (same tag replaces top section, no duplicate), foreign-anchorless (asserts the
  error names `--regenerate` **and** the file is left byte-for-byte unchanged).
- **Full regeneration** — a contract test (MockRunner) asserts every section's commits are enriched
  with the batched calls per platform, the file is overwritten, and anchors are present.
- **GitLab full-regen warning** — surfaced by the pipeline step.
- **Custom `header` + incremental** — a run with `rendering.templates.header` overridden still
  splices correctly, proving the anchor decouples the parser from the visible header.
- **Flag plumbing** — `--regenerate` (changelog) and `--regenerate-changelog` (release) reach the
  native generator.

## Migration (heraut itself)

Switching `.config/heraut.yml` to `generator: native` and cutting the next release will **stop**
with the foreign-anchorless error (the current `CHANGELOG.md` is git-cliff's, no anchors). Running
that release once with `--regenerate-changelog` rebuilds the file with anchors and full historical
attribution; every subsequent release is incremental and preserves the history.

## Out of scope

- Non-native generators (git-cliff keeps its own regenerate-with-enrichment behavior).
- A machine-readable changelog (YAML front matter / sidecar `changelog.json`) — front matter
  renders visibly on GitHub and does not solve section-boundary location; revisit only if a real
  consumer appears.
- A `.heraut.yml` mode knob (flags suffice).
- Backfilling missing historical releases in incremental mode (that is what `--regenerate` is for).

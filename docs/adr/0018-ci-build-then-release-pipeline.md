# ADR-0018: Self-Bootstrapping CI Release Pipeline

- **Status**: Accepted
- **Date**: 2026-05-30
- **Deciders**: bchatard

---

## Context

The v0.x release workflow (established in T02 and T33) is:

1. Developer runs `heraut release` locally — creates the changelog commit and pushes the
   tag.
2. The `push: tags: v*` trigger fires the `release.yml` workflow.
3. GoReleaser builds cross-platform binaries and creates the GitHub Release
   (`release: disable: false`).
4. The git-cliff GitHub Action generates the release notes independently and passes them
   to GoReleaser.

This works for a single developer cutting releases from a clean local environment, but it
has three structural problems that become significant before v1.0.

**Problem 1 — Full bootstrap dependency.** The release step that creates the tag must run
on a machine with a previously-installed heraut binary. If `heraut release` has a
regression, the only recovery path is a manual escape hatch: raw git + gh CLI commands
that replicate what heraut does internally. That knowledge is undocumented and fragile.

**Problem 2 — Dual release-notes generation.** The changelog content is generated by
heraut (via git-cliff), and the release notes shown on GitHub are generated again by the
`orhun/git-cliff-action` step in CI. Two code paths producing the same content from the
same config is redundant and a future drift risk.

**Problem 3 — No asset-upload path.** `heraut release` has no mechanism to attach binary
assets to the GitHub Release it creates. GoReleaser fills this gap today by owning the
`gh release create` call, but this means heraut cannot fully own the release pipeline —
it stops at tagging and cedes control to GoReleaser for the platform step.

## Decision

Replace the tag-triggered, GoReleaser-owned release workflow with a three-step
self-bootstrapping pipeline triggered by `workflow_dispatch`. heraut owns the GitHub
Release; GoReleaser is reduced to a pure build tool.

### Three-step pipeline

```
Step 0  heraut version next       (previous pinned build)  →  VERSION
Step 1  goreleaser build --clean  (GORELEASER_CURRENT_TAG=$VERSION)  →  dist/
Step 2  heraut check              (fresh binary from dist/)
        heraut version next       (fresh binary — sanity check)
        heraut release --version $VERSION  (fresh binary)
```

**Step 0 — resolve version (previous build).**  
The previously-installed heraut binary (pinned in the mise toolchain) runs
`heraut version next`. This is the only step that requires a pre-existing heraut binary.
The bootstrap surface is deliberately minimal: `version next` is a pure read operation
(git log + conventional-commit parsing, no git writes, no network calls). If this step
breaks, the installed binary is updated manually — an acceptable narrow risk.

**Step 1 — build (goreleaser, build-only).**  
`GORELEASER_CURRENT_TAG=$VERSION goreleaser build --clean` produces `dist/` with all
platform binaries and ldflags baked in. No GitHub Release is created, no tag is pushed.
goreleaser continues to own cross-compilation; heraut does not replace it.

**Step 2 — preflight + sanity + release (fresh binary).**  
The CI-platform binary from `dist/` (linux/amd64) runs three operations in sequence:

1. `heraut check` — validates config, all external CLIs on PATH, and cliff config. A
   failure here aborts before any git state is written. This is the cleanest possible
   failure mode.
2. `heraut version next` — re-runs version resolution with the fresh binary and compares
   the result to `VERSION` from step 0. A mismatch means a releasable commit landed
   between steps 0 and 2, making the pre-built binaries stale. CI aborts cleanly.
3. `heraut release --version $VERSION` — the full release pipeline: changelog → commit →
   tag → push → `gh release create` with asset upload.

The binary performing the release is the binary being released. A broken release path is
fixed by pushing a code fix and re-running the workflow — no manual intervention.

### `workflow_dispatch` trigger with optional version input

The workflow is triggered manually from the GitHub Actions UI. An optional `version` input
allows overriding the computed version for hotfixes or manual corrections. When the input
is set, step 0 is skipped and the version sanity check in step 2 is also skipped — the
human made an explicit choice, and a computed mismatch is expected.

The Docker workflows (`docker-build`, `docker-merge`) remain triggered by
`push: tags: v*`. heraut pushes the tag in step 2; the Docker workflows pick it up
automatically. No change to the Docker pipeline is required.

### `--version` flag on `heraut release`

A new `--version` flag on `heraut release` causes the pipeline to skip version resolution
entirely and use the supplied value as the pre-resolved version. This is the mechanism
step 2 uses to pass the version computed in step 0 into the release pipeline without
re-running the resolver.

The flag validates the supplied value as a semver `vMAJOR.MINOR.PATCH` string and errors
early if the tag already exists locally or on remote.

### `release.assets` config field

A new `assets` array field under the `release` block in `.heraut.yml` specifies glob
patterns for files to upload when creating the GitHub or GitLab release:

```yaml
release:
  platforms:
    - github
  assets:
    - "dist/heraut_*_linux_amd64"
    - "dist/heraut_*_linux_arm64"
    - "dist/heraut_*_darwin_amd64"
    - "dist/heraut_*_darwin_arm64"
    - "dist/heraut_*_windows_amd64.exe"
    - "dist/checksums.txt"
```

Globs are expanded at release time via `filepath.Glob` relative to the working directory.
Expanded paths are passed as positional arguments to `gh release create` /
`glab release create`. A glob that matches nothing emits a warning but does not abort the
release — the release itself is valid without a specific asset.

This field completes heraut's ownership of the platform publish step. It also makes asset
upload available to any heraut user, not just heraut itself.

### goreleaser changes

`.goreleaser.yml` gains `release.disable: true`. goreleaser is now invoked as
`goreleaser build` only; it never creates a GitHub Release. The `orhun/git-cliff-action`
step is removed from `release.yml` — heraut generates the release notes internally.

## Consequences

**Positive**

- **Broken release = push a fix and retry.** No manual escape hatch knowledge required.
  The fix-commit-retry loop is the same as any other CI failure.
- **The binary being released performs the release.** Any regression in the release logic
  is caught by the release itself — there is no version skew between the tool and the
  code it is releasing.
- **Single release-notes source of truth.** heraut (via gitcliff) generates both the
  changelog commit content and the GitHub Release notes. The `orhun/git-cliff-action`
  step is removed.
- **Asset upload is a first-class feature.** `release.assets` makes binary distribution
  part of the heraut config, not a goreleaser detail. Any project using heraut can now
  attach build artifacts to its releases.
- **Minimal bootstrap surface.** The only step that depends on a previous heraut binary
  is `version next` — the most stable and read-only operation in the codebase.
- **Version sanity check.** The mismatch check between step 0 and the fresh binary
  prevents a race condition where a releasable commit lands during the build step and
  produces binaries at the wrong version.

**Negative / trade-offs**

- **workflow_dispatch is manual.** The developer must trigger the release workflow
  explicitly from the GitHub Actions UI. There is no automatic release on push to main.
  This is intentional — releases are deliberate acts — but it means a missed trigger is
  a missed release.
- **Release workflow runtime increases.** Step 1 adds a goreleaser build to every release
  run. On the current matrix (5 targets), this is approximately 2–3 minutes on
  `ubuntu-latest`. Acceptable for a release workflow that runs infrequently.
- **`goreleaser release` can no longer be used directly** to cut a heraut release.
  Developers accustomed to `goreleaser release --clean` must use the workflow instead.
  Mitigated by the `--version` input on `workflow_dispatch` for edge cases.
- **Mid-flight failure still leaves dirty state** (tag pushed, GitHub Release created, but
  upload failed). This is an existing limitation of the release pipeline and is tracked
  separately as a future task (see `.claude/notes/mid-flight-failure.md`). The three-step
  pipeline does not make this worse — it only shifts the failure boundary.

## Relation to prior ADRs

- **ADR-0012** (changelog commit ownership): unchanged. The changelog commit and push
  still happen inside `heraut release`; only the trigger mechanism changes.
- **ADR-0013** (raw binary format): unchanged. goreleaser still produces raw binaries in
  `dist/`; heraut uploads them via `release.assets`.
